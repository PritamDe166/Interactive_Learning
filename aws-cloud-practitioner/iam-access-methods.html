Console, CLI, SDK & access keys

  • Three ways in: the Management Console (browser), the AWS CLI (terminal) and the AWS SDKs (your code). All three call the same AWS APIs.
  • The console uses a password + MFA. The CLI and SDK use access keys: an access key ID (like a username) and a secret access key (like a password).
  • Every route passes the same IAM check. The CLI and SDK don't bypass anything.
  • Long-term keys never expire on their own; temporary credentials (roles, IAM Identity Center) do, so prefer them.

Points to remember

  1. Console = browser, for people; protected by password + MFA. CLI = terminal commands and scripts. SDK = libraries for application code (.NET, Python, Java, JavaScript, Go…).
  2. All three call the same AWS APIs, and IAM evaluates every call the same way. AccessDenied in the CLI means a missing permission.
  3. An access key = access key ID (starts with AKIA) + secret access key. Temporary credentials add a session token.
  4. A user can have console access, access keys, both or neither. Up to two access keys per user (to rotate without downtime).
  5. Never share keys, commit them to Git, paste them in tickets or chat, or hard-code them in code. Never create root access keys.
  6. Long-term keys work until you delete them. Temporary credentials (IAM roles, IAM Identity Center, aws configure sso) expire automatically: prefer them.
  7. Code running on AWS (EC2, Lambda, ECS) should use an IAM role, not stored keys. The SDK finds role credentials automatically.
  8. aws configure stores keys in ~/.aws/credentials and Region/output in ~/.aws/config. Profiles (--profile) keep several accounts apart.
  9. aws sts get-caller-identity shows which identity the CLI is using: the first command to run when something is denied.

In the console and terminal

Set up the CLI (from the course hands-on)
  1. Install AWS CLI v2; check with aws --version.
  2. In IAM, open your user → Security credentials → Create access key (choose "CLI"). Copy the secret now; it's shown only once. (For a learning account only; at work prefer IAM Identity Center.)
  3. Run aws configure: access key ID, secret access key, default Region (e.g. ap-south-1), output format (json, table, text, yaml).
  4. Check who you are: aws sts get-caller-identity. List users: aws iam list-users.
  5. Remove your user from the admin group and run it again: AccessDenied … iam:ListUsers. Same rule as the console.
  6. Better for real work: aws configure sso (IAM Identity Center) or aws login (CLI 2.32+), both give temporary credentials.
  7. Delete course access keys when you're done.

Troubleshooting: "Unable to locate credentials" → configure or pick a profile. "AccessDenied" → check identity, then policies. Resource "missing" → wrong Region (--region).

Exam cheat-sheet

  • Run AWS commands from a terminal→AWS CLI
  • Call AWS from application code→AWS SDK
  • Programmatic credential with a secret→Access key
  • App on EC2 needs AWS access→IAM role, not access keys
  • Keys committed to a public repo→Deactivate/delete immediately, then rotate
  • Benefit of temporary credentials→They expire automatically
