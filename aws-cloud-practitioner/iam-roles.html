IAM roles for AWS services

  • An IAM role is an identity with permissions but no password and no long-term keys. Something assumes it and gets temporary credentials.
  • AWS services use roles to act on your behalf: an EC2 instance reading S3, a Lambda function writing to DynamoDB, CloudFormation creating resources.
  • A role has two policies: a trust policy (who may assume it) and permissions policies (what it may do).
  • Roles also give another AWS account or federated users (company directory, IAM Identity Center) access without creating IAM users.

Points to remember

  1. A role = permissions without long-term credentials. Whoever assumes it receives temporary credentials (key ID + secret + session token) from AWS STS that expire automatically.
  2. User vs role: a user is one person/workload with long-term credentials; a role is assumed by whoever is trusted, for a session.
  3. Trust policy = who can assume (the "trusted entity": an AWS service, another account, a federated user). Permissions policy = what the role can do. A role needs both.
  4. Common service roles: EC2 instance role (attached via an instance profile), Lambda execution role, CloudFormation service role.
  5. Exam pattern: "an app on EC2 needs to access S3/DynamoDB" → attach an IAM role. Never store access keys on the instance.
  6. Cross-account access: create a role in the account that owns the resources and let the other account assume it.
  7. Federation / IAM Identity Center: people from a corporate directory sign in once and assume roles; no IAM users needed.
  8. Service-linked roles are created and owned by an AWS service; you can view but not edit their permissions.
  9. Course hands-on: role DemoRoleForEC2, trusted entity AWS service → EC2, permissions IAMReadOnlyAccess. It's used later in the EC2 section.

In the console

Create DemoRoleForEC2 (from the course hands-on)
  1. IAM → Roles → Create role.
  2. Trusted entity type: AWS service; service / use case: EC2. This writes the trust policy (Principal ec2.amazonaws.com).
  3. Attach permissions: IAMReadOnlyAccess.
  4. Name it DemoRoleForEC2, review the trusted entity and permissions, Create role.
  5. The role does nothing yet. It becomes useful when attached to an EC2 instance (EC2 section): then aws iam list-users works on the instance without any aws configure.

Exam cheat-sheet

  • EC2 / Lambda needs to call AWS, no keys→IAM role
  • Another AWS account needs access→Cross-account role
  • Corporate directory users sign in to AWS→Federation / IAM Identity Center (roles)
  • Who may assume the role→Trust policy
  • Role credentials→Temporary, from STS, expire automatically

Check yourself

Answer out loud before you open each card.

Can you sign in to the console "as a role" with a password?Show answer

No. Roles have no password or long-term keys; they're assumed (for example by switching role from a signed-in user, or through SSO).

What are the two policies every role has?Show answer

Trust policy (who can assume it) and permissions policy (what it can do).

Which service hands out the temporary credentials?Show answer

AWS STS (Security Token Service).

Why is a role safer than keys on an EC2 instance?Show answer

Nothing long-term is stored; credentials rotate automatically and expire, so a stolen copy soon stops working.

Name three AWS services that commonly use roles.Show answer

EC2, Lambda, CloudFormation (also ECS tasks and many others).

A partner company's AWS account must read one of your buckets. Create them IAM users?Show answer

No: create a cross-account role they can assume (or use a bucket policy naming their account).
