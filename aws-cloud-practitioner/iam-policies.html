IAM policies

  • A policy is a JSON document: Effect (Allow / Deny) + Action (API calls) + Resource (which things), optionally a Condition.
  • For every request AWS gathers all policies that apply and decides: explicit Deny wins, otherwise an Allow lets it through, otherwise it's denied by default.
  • Policies on users, groups and roles are identity-based (no Principal). Policies on resources, like S3 bucket policies, are resource-based and name a Principal.
  • AWS managed policies (AdministratorAccess, IAMReadOnlyAccess) are maintained by AWS; customer managed ones are yours; inline ones are embedded in one identity.

Points to remember

    
    
      
  1. Policies are JSON. Version is the policy-language version, normally "2012-10-17" (not your revision number).
    2. 
      
  2. Statement holds one or more statements. Each has Effect (Allow or Deny), Action (API calls like s3:GetObject) and Resource (ARNs). Sid (a label) and Condition are optional.
    3. 
      
  3. Principal says who: used in resource-based policies (S3 bucket policy, role trust policy). Identity-based policies don't need it; the identity is where it's attached.
    4. 
      
  4. Evaluation order: default deny → any explicit Deny? → any Allow? An explicit Deny always wins, no matter how many Allows.
    5. 
      
  5. Permissions from every source add up: group policies + directly attached policies + inline policies.
    6. 
      
  6. Wildcards: "Action": "*", "Resource": "*" with Allow = full admin (AdministratorAccess). iam:Get* and iam:List* = read-only (IAMReadOnlyAccess).
    7. 
      
  7. Condition limits when: require MFA, a source IP range, a Region, a tag, or your AWS Organization.
    8. 
      
  8. Kinds: AWS managed (reusable, AWS updates them), customer managed (reusable, yours), inline (embedded in one user/group/role; harder to audit).
    9. 
      
  9. SCPs (Organizations) and permission boundaries only set a maximum. They never grant anything on their own.
    10. 
      
  10. The same evaluation applies whether the call comes from the console, CLI or SDK. AccessDenied names the missing action, such as iam:ListUsers.
    11.

    2.

    3. 
        
  3. Attach IAMReadOnlyAccess directly to the user. Listing users works again; creating a group is denied (read-only).
    4. 
        
  4. Create a temporary developers group, add the user, attach a harmless policy. Add the user back to admin. The user now shows three permission sources: two groups + one direct.
    5. 
        
  5. Open Policies → AdministratorAccess → JSON: "Effect": "Allow", "Action": "*", "Resource": "*".
    6. 
        
  6. Open IAMReadOnlyAccess: actions like iam:Get* and iam:List*.
    7. 
        
  7. Create policy with the visual editor: IAM, allow ListUsers and GetUser, all resources. Name it MyIAMPermissions and compare the generated JSON.

Exam cheat-sheet

    
    
      
  • Element that lists API calls→Action
    • 
      
  • Element that says who (in a bucket policy)→Principal
    • 
      
  • Restrict by IP, MFA, Region, tag→Condition
    • 
      
  • Allow s3:* plus Deny s3:DeleteObject, then a delete→Denied (explicit Deny wins)
    • 
      
  • No policy mentions the action→Denied (implicit deny)
    • 
      
  • "Action": "*", "Resource": "*"→Administrator access
    • 
      
  • SCP allows it but no IAM policy does→Denied (SCPs grant nothing)

Check yourself

    
Answer out loud before you open each card.

    

      
What does "Version": "2012-10-17" mean?Show answer
The policy language version, not the date you wrote the policy.

      
A user has AdministratorAccess and one policy that denies ec2:TerminateInstances. Can they terminate an instance?Show answer
No. The explicit Deny overrides the Allow.

      
Why does an S3 bucket policy have a Principal but a group policy doesn't?Show answer
A bucket policy is resource-based, so it must say who is allowed. A group policy is identity-based: the "who" is whoever it's attached to.

      
What does iam:List* allow?Show answer
Every IAM action starting with List: ListUsers, ListGroups, ListRoles…

      
Which element would you use to require MFA?Show answer
Condition, for example "Bool": {"aws:MultiFactorAuthPresent": "true"}.

      
Inline vs managed policy: which is easier to reuse and audit?Show answer
Managed (AWS or customer). Inline policies are embedded in one identity.
