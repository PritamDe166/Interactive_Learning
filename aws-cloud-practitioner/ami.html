AMIs: Amazon Machine Images

  • An AMI is the template an EC2 instance is launched from: OS, installed software, configuration.
  • Sources: public (e.g. Amazon Linux from AWS), your own custom AMIs, or AWS Marketplace (vendors, sometimes paid).
  • A custom AMI = EBS snapshots of the instance's volumes + launch metadata. Software baked in means faster boots.
  • An AMI belongs to one Region: use it in any AZ there; copy it to use in another Region.

Points to remember

  1. AMI = Amazon Machine Image: a reusable template for launching EC2 instances.
  2. Three sources: Public (AWS, e.g. Amazon Linux 2023), Custom (you make and maintain it), AWS Marketplace (vendor-built, may cost extra).
  3. Why custom: faster boot and setup (software pre-installed), consistent servers, repeatable deployments (Auto Scaling launches from an AMI).
  4. Process: launch → customise → (ideally) stop for data integrity → Create image → status pending → available → launch from My AMIs.
  5. Creating an AMI also creates EBS snapshots of every volume attached to the instance. Deleting those snapshots breaks the AMI.
  6. An AMI is Region-scoped: launch in any AZ of that Region; copy the AMI to use it in another Region.
  7. AMIs are immutable: to change one, launch from it, change the instance, create a new AMI.
  8. You pay for the AMI's storage (its snapshots), in every Region you copy it to.
  9. Snapshot vs AMI: you can't launch an instance from a snapshot; you need an AMI. Snapshot = the data; AMI = data + how to boot it.
  10. User data still works with a custom AMI, for small per-instance tweaks (e.g. write a config file).

In the console

Bake and launch a custom AMI (from the course hands-on)
  1. Launch an instance: Amazon Linux, t2.micro/t3.micro, the security group that allows HTTP. In User data, paste the script that installs and starts httpd but leave out the line that writes index.html.
  2. Wait 1–2 minutes (running ≠ ready). Open http://<public IP>: the Apache test page appears.
  3. Select the instance → Actions → Image and templates → Create image, name it demo image → Create.
  4. AMIs page: status pending, then available.
  5. Select the AMI → Launch instance from AMI (or in the wizard: My AMIs). In User data paste only the line that writes "Hello World" to index.html.
  6. The new page appears almost at once: Apache was already in the image.
  7. Clean up: terminate both instances (and deregister the AMI and delete its snapshot if you don't need them).

Cheat-sheet

  • Pre-installed software, faster launch→Custom AMI
  • Ready-made commercial software image→AWS Marketplace AMI
  • Launch the same server in another Region→Copy the AMI to that Region
  • Launch in another AZ of the same Region→Just launch from the AMI
  • Automate building and testing AMIs→EC2 Image Builder

An AMI created from the instance includes every attached volume; an AMI created from one snapshot includes only that volume.

Stopping before Create image is recommended, not required: by default AWS reboots the instance to get a consistent image (you can choose "no reboot").

Check yourself

Can you launch an EC2 instance directly from an EBS snapshot?Show answer

No. You need an AMI (which can be created from the snapshot).

An AMI made in us-east-1. Can you launch it in us-east-1b?Show answer

Yes. AMIs work across all AZs of their Region.

…and in eu-west-1?Show answer

Only after you copy the AMI to eu-west-1.

You need to update the software in an AMI. How?Show answer

AMIs are immutable: launch from it, update the instance, create a new AMI (or automate with EC2 Image Builder).

Why does a custom AMI shorten scale-out time?Show answer

The software is already installed, so new instances only boot and run small user data.

Who maintains a custom AMI?Show answer

You (patching, rebuilding). It's your OS and software.
