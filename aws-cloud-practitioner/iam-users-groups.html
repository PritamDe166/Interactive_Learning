IAM users & groups

  • IAM (Identity and Access Management) decides who can get into your AWS account and what they can do. It is a global service.
  • The root user is created with the account and can do everything; don't use it for daily work.
  • An IAM user is one person or workload. A group is a set of users; groups can't contain groups.
  • Policies (JSON permission documents) are attached to groups, and every member inherits them. Give only what's needed: least privilege.

Points to remember

  1. IAM = authentication + authorization: who you are, and what you're allowed to do.
  2. IAM is global: users, groups, roles and policies are not created in a Region.
  3. The root user is created automatically with the account and has full access. Use it only for root-only tasks; protect it with MFA.
  4. One IAM user = one person (or one workload). Never share users or credentials.
  5. Groups contain users only, never other groups. A user can be in several groups, or in none.
  6. Permissions come from policies, JSON documents attached to users, groups or roles. A user gets the union of everything attached to them and their groups.
  7. Default is deny: with no policy allowing an action, the request fails.
  8. Least privilege: grant only what each job needs. "Give everyone AdministratorAccess" is the wrong answer.
  9. Prefer attaching policies to groups over attaching them to individual users.
  10. For real organisations AWS recommends IAM Identity Center (single sign-on) for people; IAM users are fine for learning.

In the console

Create an admin user in a group (from the course hands-on)
  1. Open IAM (search "IAM"). The Region selector shows Global: IAM isn't regional.
  2. Check the top-right menu: only an account ID means you're signed in as root.
  3. Users → Create user, give a name, tick console access, and choose a password (for someone else: autogenerated + reset at first sign-in).
  4. On permissions, add the user to a group: create group admin and attach AdministratorAccess. (Fine for your own learning account; too broad for real users.)
  5. Optional tags, such as Department = Engineering, help with ownership and reporting.
  6. Open the group and check the user is listed; open the user and see the policy shown as inherited from the group.
  7. Set an account alias so the sign-in URL is https://<alias>.signin.aws.amazon.com/console (alias must be globally unique).
  8. Sign in as the new user in a private window. The top-right now shows user @ account. Use this user, with MFA, for daily work.

Common mistakes: using root daily, giving everyone AdministratorAccess, attaching policies user by user, unclear group names like test.

Exam cheat-sheet

  • Who can do what in AWS→IAM
  • Account owner, full access, use rarely→Root user
  • Collection of users→IAM group
  • JSON document of permissions→IAM policy
  • Give only the permissions needed→Least privilege
  • Can a group contain a group?→No

Check yourself

Answer out loud before you open each card.

Is IAM a regional or a global service?Show answer

Global. Users, groups and policies apply to the whole account.

Charles is in Developers and Audit. Which permissions does he get?Show answer

Both groups' permissions combined (plus anything attached to him directly).

Fred is in no group and has no policies. Can he list EC2 instances?Show answer

No. The default is deny; nothing allows it.

Can you put the "Developers" group inside an "Engineering" group?Show answer

No. IAM groups contain users only.

Ten developers need the same access. What's the least effort, most maintainable way?Show answer

Create a group, attach the policy to it, add the ten users.

Why shouldn't two people share one IAM user?Show answer

Accountability and control: you can't tell who did what, and removing one person's access locks out the other.
