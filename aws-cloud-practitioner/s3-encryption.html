AWS CLF-C02 / Amazon S3 / 7 · Domain 2 Security

S3 Encryption

  • In transit, S3 uses HTTPS (TLS). At rest, every new object is encrypted with SSE-S3 by default since January 2023.
  • SSE-KMS uses keys you control in AWS KMS, with every use logged in CloudTrail.
  • SSE-C: S3 encrypts with a key you send. Client-side: you encrypt before uploading.
  • A bucket policy can force HTTPS or a particular encryption.

Points to remember

  1. In transit: HTTPS/TLS to S3 endpoints. A bucket policy can deny non-HTTPS requests.
  2. SSE-S3 (AES-256, S3-managed keys) is applied to all new objects by default since 5 Jan 2023, at no cost, and can't be disabled.
  3. SSE-KMS: keys in AWS KMS; you control access and rotation; usage is audited in CloudTrail; KMS charges apply.
  4. DSSE-KMS: two layers of KMS encryption for strict compliance.
  5. SSE-C: you supply the key in every request; S3 doesn't store it; HTTPS only.
  6. Client-side: you encrypt before upload; you manage keys and process.
  7. Shared responsibility: AWS provides the encryption; you choose the method and manage your keys.

In the console

Check and change encryption (outline)
  1. Upload a file, open it → Properties → Server-side encryption: SSE-S3 is already applied.
  2. Bucket → Properties → Default encryption → Edit: switch to SSE-KMS and pick a KMS key (the AWS-managed aws/s3 key or your own). Leave Bucket Key enabled.
  3. Upload another file: it now shows SSE-KMS. Earlier objects keep SSE-S3 until copied.

Cheat-sheet

  • Encrypted at rest by default→SSE-S3
  • Control and audit encryption keys→SSE-KMS
  • Encrypt before upload→Client-side encryption
  • Your key, S3 encrypts, AWS never stores it→SSE-C
  • Protect data moving to S3→HTTPS / TLS
  • Force HTTPS on a bucket→Bucket policy: Deny aws:SecureTransport false
  • Find sensitive data in buckets→Amazon Macie
