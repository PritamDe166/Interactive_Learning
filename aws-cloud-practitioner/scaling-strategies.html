AWS CLF-C02 / ELB & Auto Scaling / 4 · Domain 3 Technology

Auto Scaling Strategies

  • A scaling policy decides when an Auto Scaling group changes its desired capacity.
  • Dynamic policies react to a metric: simple and step scaling follow CloudWatch alarms; target tracking keeps a metric (for example CPU 50%) steady.
  • Scheduled scaling changes capacity at set times; predictive scaling forecasts daily patterns with machine learning and scales ahead of them.
  • Real setups often combine them: predictive for the known pattern, target tracking for surprises.

In terms you know

PolicyClosest thing you knowThe difference
Target trackingA thermostat set to 21 °CIt keeps a metric such as average CPU at the value you choose, adding or removing instances as needed.
Scheduled scalingA Windows Task Scheduler job that starts extra servers at 8 amBuilt into the ASG; it changes min, desired or max at the times you set.
Simple / step scalingA monitoring alert that runs a script to add a serverA CloudWatch alarm triggers the ASG directly; step scaling adds more when the breach is bigger.

Points to remember

  1. Manual (or fixed): you set desired capacity yourself. Fine for steady load; wasteful or overloaded otherwise.
  2. Simple scaling: a CloudWatch alarm (for example CPU above 70%) adds or removes a set number of instances, then waits for a cooldown before acting again.
  3. Step scaling: like simple scaling, but the size of the change depends on how far the alarm is breached (+1 above 70%, +3 above 90%).
  4. Target tracking: pick a metric and a target (average CPU 50%, requests per target 1,000) and the ASG keeps it there. The easiest to set up and the one AWS recommends first.
  5. Scheduled: change capacity at known times (for example 8 instances from 08:00 on weekdays). For predictable events.
  6. Predictive: machine learning forecasts load from at least a day of history and launches capacity before the peak.
  7. New instances need time to boot and warm up, so reactive policies always lag a little; scheduled and predictive scaling get ahead of known peaks.

Which scaling policy fits?

In the console

Add scaling policies to an Auto Scaling group (outline)
  1. EC2 → Auto Scaling groups → pick the group → Automatic scaling tab.
  2. Create dynamic scaling policy → Target tracking: metric "Average CPU utilization", target value 50. The ASG creates the CloudWatch alarms for you.
  3. For step or simple scaling, first create a CloudWatch alarm, then choose it in the policy and set the adjustments.
  4. Create scheduled action: for example desired 8, min 4 every weekday at 08:00 (cron), and desired 2 at 22:00.
  5. Create predictive scaling policy: start in forecast only mode to check the forecast, then switch to forecast and scale.

Cheat-sheet

  • Keep average CPU around 40%→Target tracking
  • CloudWatch alarm adds 2 instances when CPU > 70%→Simple (or step) scaling
  • Bigger breach, bigger change→Step scaling
  • Known event: sale starts Friday 9 am→Scheduled scaling
  • Repeating daily or weekly pattern, scale before it→Predictive scaling (machine learning)
  • Steady load that never changes→Fixed / manual capacity

Good metrics to scale on: average CPU, requests per target (from the ALB), average network in or out, or a custom CloudWatch metric such as queue length.

Cooldown and warm-up. After a simple-scaling action the group waits (300 seconds by default) before another one. Target tracking and step scaling use an instance warm-up time instead, so a booting instance isn't counted too early.

Several policies at once. When policies disagree, the ASG uses the one that gives the largest capacity, so the app is never under-provisioned by a cautious policy.

Check yourself

Answer out loud before you open each card.

"Keep average CPU at 40%." Which policy?Show answer

Target tracking.

A ticket sale starts every Friday at 09:00. How do you have capacity ready in time?Show answer

Scheduled scaling (raise capacity shortly before 09:00 on Fridays). Predictive scaling could also learn a regular weekly pattern.

Which policy uses machine learning?Show answer

Predictive scaling: it forecasts load from history and scales ahead of it.

What is the difference between simple and step scaling?Show answer

Simple scaling makes one fixed change per alarm and then waits. Step scaling makes a bigger change for a bigger breach.

Why does a reactive policy still let CPU spike briefly?Show answer

It acts after the metric rises, and new instances need a few minutes to boot and warm up.

A TV advert causes a sudden one-off spike. Which policy can't foresee it?Show answer

Predictive (and scheduled) scaling: neither has seen it before. Target tracking or step scaling react to it.
