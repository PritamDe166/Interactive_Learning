IAM: Users, Groups, Policies & Roles

  • IAM decides who can do what in your account. Global and free.
  • Users: people or apps with long-term credentials. Groups: hand permissions to many users at once.
  • Policies: JSON documents that allow or deny API actions.
  • Roles: temporary credentials for whoever assumes them, such as an EC2 instance.
  • Everything starts at deny.

    Rules

    A user can be in several groups and gets the union of their policies. Groups contain users only, never other groups. Prefer attaching policies to groups rather than to individual users.

    Root user

    Created with the account, has full access, and can't be restricted by IAM policies. Use it only for root-only tasks, protect it with MFA, and never create root access keys.

    Rule of thumb

    Explicit Deny always wins. An SCP or permissions boundary only limits; it never grants. Without any Allow, the answer is the default (implicit) deny.

    Securing IAM

    MFA

    Password + something you have. Options: passkeys and security keys (phishing-resistant, preferred), virtual authenticator apps, hardware TOTP tokens. Up to 8 devices per user.

    Password policy

    Minimum length (6–128), character types, expiry (1–1,095 days), prevent reuse (up to 24). Doesn't apply to root or to access keys; there is no lockout policy.

    Access keys

    Access key ID + secret, for the CLI and SDKs. Max two per user (for rotation). Never put them in code or Git; prefer roles and temporary credentials.

    Corrected

    SMS text messages are no longer an MFA option: AWS ended support for enabling them. Older course material still lists SMS.

    Corrected

    Access Advisor isn't user-only. It shows last-accessed data for users, groups, roles and policies, and covers identity-based policies only (not SCPs or resource policies).

    Updated

    "One IAM user per person" is no longer AWS's first choice for people. Current best practice: humans sign in through IAM Identity Center (single sign-on, temporary credentials); workloads use roles; IAM users only where neither fits. For the exam, if Identity Center is an option for workforce access, it's usually right.

    Added

    Three ways to call AWS, all checked by the same IAM permissions: the Management Console (browser), the AWS CLI (terminal) and the SDKs (code). Store secrets in Secrets Manager or Parameter Store, not in code. CloudShell is handy for labs but out of exam scope.

    Check yourself

    Answer out loud before you open each card.

    A policy allows s3:* and another denies s3:DeleteObject. Can the user delete?Show answer

    No. An explicit Deny overrides any Allow.

    An app on EC2 must read a bucket. Most secure way to give it access?Show answer

    Attach an IAM role to the instance. It gets temporary credentials that rotate automatically; no keys on disk.

    Can an IAM group contain another group?Show answer

    No. Groups contain users only. A user can belong to several groups.

    Which tool shows which users have no MFA and old access keys?Show answer

    IAM credential report (account-wide CSV). Access Advisor is about services used.

    An SCP allows S3 but no IAM policy allows it for the user. Result?Show answer

    Denied. SCPs only set the maximum; something must still grant the action.

    Which policy element names who the policy applies to, and where do you see it?Show answer

    Principal, in resource-based policies such as S3 bucket policies. Identity-based policies leave it out because the identity is implied.
