Modules, packages, pip & venv

  • Every .py file is a module. import billing runs billing.py once, caches it in sys.modules, and binds the name billing.
  • from billing import tax copies just that name into your file; import numpy as np picks a shorter alias.
  • __name__ is "__main__" when a file is run directly and the module's name when it's imported, hence if __name__ == "__main__":.
  • A package is a folder of modules. pip installs third-party packages; a virtual environment (venv) keeps each project's packages separate.

Cheat-sheet

    
    
      
  • Use code from another file→import module, then module.name
    • 
      
  • A few names, used a lot→from module import name
    • 
      
  • Long module name→import pandas as pd (follow the community's alias)
    • 
      
  • Code that should only run when the file is started→if __name__ == "__main__": + main()
    • 
      
  • Group several modules→A folder = a package; import with from clinic.billing import tax
    • 
      
  • New project→python3 -m venv .venv, activate, then pip install …
    • 
      
  • Share exact dependencies→pip freeze > requirements.txt / pip install -r requirements.txt
    • 
      
  • Avoid→from x import * and naming your file like a library (random.py, json.py)

Added
Why a venv: without one, pip install puts packages into the system or user Python shared by every project, and versions clash. A venv is a folder with its own interpreter link and site-packages, like a per-project node_modules or NuGet packages folder.

      
Added
Running a package module: python -m clinic.billing runs it with the right import paths; running python clinic/billing.py directly often breaks its imports of sibling modules.

      
Updated
Newer tools: uv (Astral) creates venvs and installs packages much faster and is widely used now (uv venv, uv pip install, uv add). Project metadata lives in pyproject.toml. Plain venv + pip still works everywhere and is what the docs teach.
