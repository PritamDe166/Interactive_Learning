Client-Server & DNS

  • The client asks; the server processes and answers.
  • Before asking, the client needs the server's IP address.
  • DNS turns a name like www.example.com into that IP.
  • Caching at every level means most lookups never travel the whole chain.

Client and server

Splitting the work lets each side change and scale on its own.

Client

Browser, mobile app, desktop app.

  • Shows the UI
  • Sends requests
  • Displays responses

Server

Runs where the client can't be trusted or can't reach.

  • Business logic and authentication
  • Database access
  • Returns responses

Why it matters

The server side can grow from one machine to many behind a load balancer without the client changing. That is where Week 2 picks up.

Recursive resolver

Does the legwork for you, usually run by your ISP or a public service such as 8.8.8.8. It caches every answer.

Root → TLD → Authoritative

Root and TLD servers only point the way. The authoritative server holds the actual record.

TTL

Each record says how long it may be cached. Short TTL means changes spread quickly; long TTL means fewer lookups.

Worth knowing

Added

Your device checks more than a cache. Before asking the resolver, the operating system also reads its hosts file. That is why editing /etc/hosts can override DNS.

Added

Root servers are rarely asked. Resolvers cache the referrals too. The .com server list has a TTL of about two days, so a busy resolver almost never needs the root for .com names.

Added

Transport: classic DNS uses UDP port 53 because a query fits in one packet. It switches to TCP for large answers and zone transfers. Encrypted options exist too: DNS over HTTPS (DoH) and DNS over TLS (DoT).

When DNS fails

Healthy app, dead site

If the name can't be resolved, no request ever reaches your servers. Every hop in the path is a possible failure point.

Caches buy time

Clients that still hold a cached answer keep working until its TTL runs out. Turn on "Resolver outage" and look up with a warm cache to see it.

How big sites protect DNS

  • Several authoritative servers
  • Anycast: one IP served from many locations
  • More than one DNS provider

Check yourself

Answer out loud before you open each card.

Your API servers are healthy, but users report the site is down. Name a cause outside the app.Show answer

DNS can't resolve the name (or the load balancer or TLS is broken). Users never reach the healthy servers.

What does the root server return for www.example.com?Show answer

Not the IP. It returns a referral to the .com TLD servers. Only the authoritative server returns the A record.

You are moving to a new server IP tomorrow. What should you do with the TTL today?Show answer

Lower it in advance (for example from 1 day to 60 s), so cached copies of the old IP expire quickly after the switch.

Who does the recursive work: the browser or the resolver?Show answer

The resolver. The browser makes one request and gets one final answer; the resolver walks root, TLD and authoritative on its behalf.

Why does DNS normally use UDP rather than TCP?Show answer

A query and answer fit in one packet each, so skipping the TCP handshake saves a round trip. DNS falls back to TCP when the answer is too large.

shop.example.com should point at your CDN's hostname, not a fixed IP. Which record?Show answer

CNAME. It aliases one name to another, so the CDN can change its IPs without you editing DNS.
