TCP vs UDP

Both carry data between applications, with opposite trade-offs. TCP sets up a connection first, then guarantees every byte arrives once and in order. UDP just sends: no setup, no recovery, lower delay. The right choice depends on whether a late packet is still useful.

Same five packets, two protocols

Time flows downward · one step down ≈ one network trip
TCP · receive buffer (in the OS, before your app)
TCP · your app reads

Segments that arrive early wait in the buffer until the gap is filled.

UDP · your app reads (in arrival order)

No buffer that reorders, no retransmission. The app gets what arrives, when it arrives.

The three-way handshake

Both sides pick a random starting sequence number and confirm the other's.

1 · SYN

Client: "I want to connect; my bytes start at seq=1000."

2 · SYN-ACK

Server: "Got it, I expect 1001 next (ack=1001); mine start at seq=5000."

3 · ACK

Client: "I expect 5001 next." Now both directions are confirmed. Data can ride along with this ACK.

Why not two?

After two messages the server still doesn't know its SYN reached the client. The third message proves the client received the server's starting number, so both sides agree.

The UDP checksum is optional only on IPv4. On IPv6 it is mandatory. Either way it only detects damage; nothing repairs or resends.

HTTP versions and the transport underneath

HTTP/1.1 · TCP

Keep-alive reuses one connection for many requests, but one at a time. Browsers open ~6 connections per site to work around it.

HTTP/2 · TCP

Multiplexes many requests on one connection. But if one TCP packet is lost, every stream waits for it: head-of-line blocking.

HTTP/3 · QUIC · UDP

QUIC rebuilds reliability per stream on top of UDP, so one loss stalls only its own stream. TLS 1.3 is built in, setup takes one round trip, and connections survive a Wi-Fi → mobile switch.

Added

Why QUIC uses UDP: TCP lives in operating-system kernels and network gear, so it is hard to change. UDP is a thin, universally allowed wrapper, so QUIC can add its own reliability, ordering per stream and encryption in user space.

Check yourself

Answer out loud before you open each card.

A multiplayer game sends player positions 30 times a second. TCP or UDP?Show answer

UDP. A resent old position is worse than the next fresh one. A late packet is as bad as a lost one.

Flow control vs congestion control in one line each?Show answer

Flow control stops you overwhelming the receiver. Congestion control stops you overwhelming the network between you.

Segment 3 arrives before segment 2. What does your application see?Show answer

Nothing yet. TCP holds segment 3 in the kernel's receive buffer and hands over 2, 3 in order once 2 arrives.

How does a TCP sender learn a segment was lost, without waiting for a timeout?Show answer

Three duplicate ACKs for the same number trigger a fast retransmit. Otherwise the retransmission timer fires.

Does HTTP always run on TCP?Show answer

No. HTTP/1.1 and HTTP/2 use TCP; HTTP/3 uses QUIC, which runs over UDP.

Why does every new connection to your database cost latency?Show answer

The handshake (plus TLS if used) costs round trips before any query. That's why apps use connection pools.
