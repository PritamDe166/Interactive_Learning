HTTPS & the TLS Handshake

  • HTTPS = HTTP over TLS.
  • Job 1: prove the server's identity with a certificate.
  • Job 2: agree on shared keys during the handshake.
  • After that, everything is encrypted with fast symmetric crypto.

What TLS gives you

Confidentiality

Eavesdroppers on the Wi-Fi or ISP can't read the request or response.

Integrity

Any change in transit is detected and the connection is dropped.

Authentication

The client can verify it is really talking to api.example.com, not an impostor.

Corrected

In TLS 1.3 the server sends Finished first, in its very first reply. The client sends its Finished after checking the certificate. Client-first is the TLS 1.2 order.

Added

0-RTT resumption: a returning client can send its request inside the first TLS message. It's fastest, but an attacker could replay that early request, so servers allow it only for safe, idempotent requests such as GET.

Can I trust this certificate?

Pick a scenario, then run the browser's checks
Browser checks, in order

    What's in a certificate

    Hostname(s), the server's public key, validity dates, issuer, and the issuer's signature. The private key never leaves the server.

    How trust works

    The browser checks each signature using the issuer's public key, up to a root CA already in the OS or browser trust store. Nothing is "decrypted"; signatures are verified.

    Why a copied certificate is useless

    Certificates are public. Only the holder of the private key can sign the handshake (CertificateVerify).

    Around the handshake

    Asymmetric, then symmetric

    Public-key crypto (Diffie-Hellman, signatures) is slow but lets strangers agree on a secret. The bulk data then uses fast symmetric ciphers such as AES-GCM.

    TLS termination

    A load balancer or CDN can decrypt at the edge, which centralises certificates. Internal hops can be re-encrypted when the data is sensitive. More on Days 10–12.

    What HTTPS doesn't hide

    • IP addresses, timing and sizes
    • Usually the hostname, via SNI (unless Encrypted Client Hello is used)
    • DNS lookups, unless DoH or DoT is on

    Check yourself

    Answer out loud before you open each card.

    Name the two separate jobs TLS does.Show answer

    Authenticate the server (certificate + CertificateVerify) and agree on session keys (ephemeral Diffie-Hellman).

    Why is a TLS 1.3 handshake faster than TLS 1.2?Show answer

    One round trip instead of two: the client guesses the key exchange and sends its key share in the first message.

    An attacker records today's encrypted traffic and steals the server's private key next year. Can they decrypt it?Show answer

    Not with ephemeral (EC)DHE, which TLS 1.3 always uses: the session keys were never derived from the long-term key. That's forward secrecy.

    Why are POST requests not sent as 0-RTT early data?Show answer

    Early data can be replayed by an attacker. Replaying a payment POST could charge twice.

    The browser says "Your connection is not private" but the dates look fine. Two likely causes?Show answer

    Hostname mismatch (certificate for a different name) or an untrusted chain (self-signed, or a missing intermediate).

    Why do load balancers often terminate TLS?Show answer

    One place for certificates and renewal, less crypto work on app servers, and the balancer can read HTTP to route by path.
