Load Balancing Algorithms

A load balancer has one job per request: pick a server. Static algorithms pick by a fixed rule and never look at how the servers are doing. Dynamic algorithms look at live numbers, such as open connections or response time, before every pick. Real balancers often blend the two.

    Which one would you pick?

    Answer out loud before you open each card. This is the step that makes it stick.

    A patient-search API runs on six identical, stateless containers behind the balancer.Show answer

    Round Robin. Any container can serve any request and they are all the same size, so the simplest rule wins. Add health checks so a dead container drops out of the rotation.

    A legacy imaging viewer keeps each user's session in server memory, and you cannot move it to Redis this quarter.Show answer

    Sticky Round Robin (or hash on a session cookie). The user must return to the server that holds their session. Accept the uneven load, and plan to make the app stateless (Day 9).

    Your fleet has two new 16-core nodes and one old 4-core node that finance will not retire yet.Show answer

    Weighted Round Robin, roughly 4:4:1. Capacity differs and is known ahead of time, so fixed weights describe it well.

    Appointment-booking calls sometimes wait 5–10 seconds on a slow insurance-verification API, others return in 50 ms.Show answer

    Least Connections. Request durations vary wildly, so counting open connections steers new work away from servers stuck on slow calls. Least Response Time also works if latency is the metric you care about.

    Three cache nodes sit in front of the provider directory, and the same URL should always hit the same node so it stays warm.Show answer

    Hash on the URL. Watch out: adding a fourth node with plain mod-N remaps most keys and empties every cache at once. Consistent hashing (Day 54) fixes that.
