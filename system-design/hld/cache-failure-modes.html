Week 3 / H20 / Caching & CDN

Caching Failure Modes

  • A cache keeps load away from the database. This page shows the moments when it stops doing that.
  • Stampede: one popular key expires, and every request loads it from the database at the same time.
  • Avalanche: many keys expire at the same time, or a cache server goes down.
  • Penetration: requests for data that doesn't exist always go to the database.
  • Hot key and stale data are two more problems. Each of the five has a standard fix.

4Revise in two minutes

Cheat-sheet

  • A popular key expires and the database load jumps→Stampede: let one request load it (single-flight or a lock), or serve the old value while one refresh runs
  • Many app servers, still a jump→A lock shared by all servers (Redis SET NX: set the key only if it does not exist yet), or refresh the key before it expires
  • A load spike at the same time every day→Avalanche: add random jitter to expiry times; warm the cache in stages
  • Cache server restarted and the database is overloaded→Avalanche: replicas, persistence, and a limit on queries reaching the database
  • Misses for IDs that don't exist→Penetration: cache "not found" for a short time, use a Bloom filter, check the input
  • One cache server is overloaded, the others are idle→Hot key: keep a short local copy on each app server, or copy or split the key
  • Users see old values→Stale data: delete the key when you write, and always set a TTL (H17)

Early refresh by chance (XFetch): on each read, make a random choice. The closer the key is to expiry, the more likely the choice is "refresh now". The formula is now − delta × beta × ln(random()) ≥ expiry, where delta is how long a reload takes and beta is about 1. Long before expiry, almost no request refreshes. Close to expiry, one request refreshes first, so the key never actually expires. No lock is needed.
Jitter fixes avalanches, not stampedes. For one popular key, jitter only moves the moment it expires. For that key, use single-flight, stale-while-revalidate or early refresh.
Other names you may see: some sources call one popular key expiring a cache breakdown (this page calls it a stampede). Penetration and avalanche mean the same as here.
Big keys are values of several MB, or lists with millions of items. Redis does one command at a time, so reading, deleting or moving a big key makes every other request wait. Split big keys into smaller ones. Delete them with UNLINK, which frees the memory in the background, instead of DEL.
When the cache itself is slow or down: use short timeouts on cache calls. Add a circuit breaker that skips the cache for a while after repeated failures. Limit how many queries can reach the database. Retry with a growing wait plus a random extra delay, so clients don't all retry at the same moment.
In interviews, a stampede question is often followed by questions on avalanche, penetration, hot keys and stale-while-revalidate.
In .NET, HybridCache and ASP.NET Core output caching both let only one request load a missing key; the others wait for it. This works inside one process. With many servers, each server still loads the key once.

5Test yourself

Which pattern fits?

Explain it out loud

Answer before you open each card.

Stampede vs avalanche: what's the difference?Show answer

Stampede: many requests for one key at the same moment. Avalanche: many keys missing at the same moment, because they had the same expiry time or the cache was lost.

Single-flight solves the stampede on one server. Why can 20 servers still hurt?Show answer

Each server has its own lock, so up to 20 loads run, one per server. If 20 is too many, use a lock shared by all servers, stale-while-revalidate, or refresh the key before it expires.

What does stale-while-revalidate trade away?Show answer

Freshness, for a short time. Users get the old value straight away while one refresh runs. That's fine for a product list, but wrong for a bank balance or stock at checkout.

How does a Bloom filter stop penetration, and what can't it do?Show answer

A Bloom filter is a small, fast set of all valid IDs. It answers "definitely not here" or "maybe here". For "definitely not here", the request never reaches the database. It is sometimes wrong when it says "maybe", but never wrong when it says "no". You also can't easily remove an ID from it.

Why add jitter instead of just a longer TTL?Show answer

A longer TTL only moves the problem later: all the keys still expire together, just at a different time. Jitter gives each key a slightly different expiry, so they never all expire at once.

"Update the DB, then delete the key" — how can the cache still end up stale?Show answer

A reader misses, reads the old row, and is slow to put it in the cache. Meanwhile a writer updates the database and deletes the key. Then the reader's late SET puts the old value back. Fixes: always set a TTL. Delete the key a second time a moment after the write. Store a version number and never overwrite newer data with older. Or delete keys from the database's change feed (CDC, change data capture).

The cache cluster restarts during peak. What protects the database?Show answer

Replicas and persistence, so the cache comes back with its data. Also a limit on queries to the database and a circuit breaker, so an empty cache can't flood the database.
