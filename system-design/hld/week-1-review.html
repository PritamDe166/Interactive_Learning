Timeline ≠ stack

The timeline runs DNS → TCP → TLS → HTTP because things happen in that order. The stack is drawn HTTP over TLS over TCP over IP because each layer carries the one above. DNS isn't "below" HTTP: it's another application protocol, usually over UDP.

Check yourself

Answer out loud before you open each card.

Explain the lifecycle of an HTTPS request in four steps.Show answer

DNS finds the IP → TCP three-way handshake → TLS handshake (identity + keys) → HTTP request and response over the encrypted channel.

Users in the US say your Bengaluru-hosted API is slow, but server time is 20 ms. Why?Show answer

Round trips × distance. At ~230 ms RTT, TCP + TLS + HTTP cost ~0.7 s before any server work. Fixes: CDN/edge, connection reuse, TLS 1.3, HTTP/3, or a US region.

Why does reusing connections matter so much?Show answer

It skips the TCP and TLS handshakes, which are pure round trips. That's why browsers keep connections alive and services use pools.

Which layer adds the IP addresses, and which adds the ports?Show answer

IP adds source/destination addresses (which machine). TCP/UDP adds ports (which program on that machine).

Is DNS "below" HTTP in the stack?Show answer

No. DNS is a separate application protocol, usually over UDP. It just happens first in time.

HTTPS is on. What can someone on the café Wi-Fi still learn?Show answer

IP addresses, timing, sizes and usually the hostname (SNI). Not the path, headers or body.

Timings are a simple model: one RTT per handshake round, fixed 50 ms server time, ~30 ms for an uncached DNS lookup. Sources: "The request, TCP explained", "Diagrams explained", and Days 1–6.
