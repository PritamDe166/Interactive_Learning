Cache Read Strategies

  • A read strategy answers one question: who loads the data when the cache misses?
  • Cache-aside: your code checks the cache, reads the DB on a miss and fills the cache.
  • Read-through: same flow, but the cache layer does the loading for you.
  • Refresh-ahead: hot keys are reloaded before they expire, so nobody waits on a miss.
  • The TTL and the cache key decide how fresh and how reusable each entry is.

4Revise in two minutes

Cheat-sheet

  • "Add a cache" with no other detail→Cache-aside + TTL + delete on write
  • Many services load the same data the same way→Read-through (one loader in the cache layer)
  • Rebuild is slow and the key is hot→Refresh-ahead
  • Data changes often, staleness hurts→Short TTL, or invalidate on write (H17)
  • Same data per tenant or per language→Put tenant/lang in the key: t:7:product:12:en
  • Schema of the cached object changed→Bump a version in the key: product:12:v3

5Test yourself

Which pattern fits?

Explain it out loud

Answer before you open each card.

Cache-aside and read-through make the same trips. So what's actually different?Show answer

Who owns the loading code. In cache-aside every caller checks, loads and stores. In read-through the cache layer has the loader, so callers just ask the cache.

Why is the first request after a deploy slower even with a cache?Show answer

The cache is cold. Lazy strategies only fill on a miss. Pre-warm the hottest keys, or use refresh-ahead for them.

Your TTL is 10 minutes and data changes every minute. What do users see?Show answer

Up to 10-minute-old data. Shorten the TTL or delete the key when the data changes.

Two tenants share a Redis. What must the key include?Show answer

The tenant ID (tenant:7:product:12). Otherwise tenant A can be served tenant B's data.

When is refresh-ahead a bad idea?Show answer

When keys are cold or unpredictable. You pay to reload entries nobody reads again.

Hit ratio is 95%, hit = 2 ms, miss = 27 ms. Average latency?Show answer

≈ 3.25 ms. 0.95 × 2 + 0.05 × 27. The misses are 5% of requests but over a third of the time.
