Cache Patterns at a Glance

  • Every cache design answers four questions: who loads on a miss, when writes reach the database, what gets evicted, and what happens when it goes wrong.
  • Read path: cache-aside, read-through, refresh-ahead. Write path: write-through, write-behind, write-around, invalidate.
  • Eviction: LRU, LFU and TTL decide what leaves a full or ageing cache.
  • Failure modes (stampede, penetration, hot key) are what interviewers probe after you say "add Redis".

Cheat-sheet

  • Read-heavy, a slow first read is fine→Cache-aside + TTL
  • Reads must see the latest write→Write-through (or invalidate on write)
  • Huge write rate, a few seconds of loss is OK→Write-behind
  • Written often, rarely read back→Write-around
  • Expensive to rebuild, must never be slow→Refresh-ahead
  • Data changed: update or delete the key?→Delete it; the next read refills
  • Hot key expires, DB spikes→Stampede: single-flight, stale-while-revalidate, TTL jitter
  • Lookups for IDs that don't exist→Penetration: cache "not found", Bloom filter
  • One key, one overloaded cache node→Hot key: local L1 copy or replicas
  • Static files, users worldwide→CDN (pull by default, push for big launches)

Write-around, invalidate-on-write, cache penetration, hot keys and CDN push vs pull are common interview follow-ups, so they have cards here.
HybridCache (package Microsoft.Extensions.Caching.Hybrid) has been generally available since March 2025 and is the recommended default for new ASP.NET Core code. Its stampede protection covers one process; ten app servers can still send ten loads to the database.
TTL expiry and eviction are different things: expiry removes a key because it is old, eviction removes one because memory is full. Redis does both, and its eviction policy (maxmemory-policy, e.g. allkeys-lru, allkeys-lfu) is a setting you choose.

Explain it out loud

Answer before you open each card.

Why delete the cache key on update instead of writing the new value into it?Show answer

Two writers can race. Request 1 writes v1 to the DB, request 2 writes v2 to the DB and cache, then request 1's late cache write puts v1 back: the cache is stale until TTL. A delete can't put an old value back; the next read loads whatever the DB has.

Write-behind looks fastest. What do you give up?Show answer

Durability. Writes are acknowledged before the database has them, so a cache crash loses the buffer. Fine for view counters, wrong for payments.

You use HybridCache on 12 app servers. Can a stampede still hit the database?Show answer

Yes, up to 12 loads. Single-flight is per process. Add TTL jitter, stale-while-revalidate, or a distributed lock if even 12 is too many.

A nightly report scans every product once. Which eviction policy protects your hot keys?Show answer

LFU. Under LRU every scanned key becomes "most recent" and pushes the hot keys out. LFU sees they were read once and evicts them first.

Bots request patient IDs that don't exist and the DB is busy. Why doesn't the cache help, and what fixes it?Show answer

Nothing is ever stored, so every request misses. Cache the "not found" result with a short TTL, or check a Bloom filter of valid IDs first, and rate-limit the client.

Pull CDN or push CDN for a 2 GB game patch released at 9:00 worldwide?Show answer

Push (or pre-warm). With pull, the first users in every region miss at the same moment and all edges hit the origin together: a stampede at CDN scale.
