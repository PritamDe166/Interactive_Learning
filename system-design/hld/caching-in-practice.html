4Revise: the answer template

"Add caching to this design": say it in this order

  1. What and why. Which reads are hot, how stale each may be (price: seconds; reviews: minutes), and the read/write ratio.
  2. Where. Browser and CDN for public, static or shared pages; L1 in-process for tiny hot data; Redis for shared data; DB last.
  3. Read pattern. Usually cache-aside with a TTL. Name the key, e.g. product:{id}:v3.
  4. Write and invalidation. Update the DB, then delete the key. Across servers: pub/sub. Across services: change events (outbox).
  5. Size and eviction. Hot data × overhead × replicas ÷ 0.7 headroom; allkeys-lru or LFU; keep values small.
  6. Failures. Stampede (single-flight, SWR), avalanche (TTL jitter), penetration (cache NULL), hot key (L1), cache down (fall back to the DB with rate limits).
  7. Measure. Hit ratio, evictions, memory, p99, DB load, origin offload at the CDN.

Cheat-sheet

  • L1 copies disagree across servers→Pub/sub invalidation + short L1 TTL
  • Another service caches your data→Outbox + change events; subscriber deletes its key
  • Campaign links lower the CDN hit ratio→Drop utm_* from the cache key
  • Page differs by language→Vary: Accept-Language (never Vary: Cookie on public pages)
  • Logged-in or per-user response→Cache-Control: private or no-store
  • One Redis call slows all others→Big key: split, page or compress it
  • New cluster or region going live→Warm the top N keys first
  • Rate limit, lock, top-10 list→INCR + EXPIRE · SET NX PX · sorted set

Explain it out loud

Answer before you open each card.

Why delete the cache key after the DB write, not before?Show answer

Deleting first leaves a gap: a reader can miss, load the old row and put it back before your write commits. Delete after the write (and keep a TTL as a safety net).

Redis pub/sub drops messages for a server that is restarting. Is that a problem for L1 invalidation?Show answer

Only briefly. A restarting server starts with an empty L1, so it has nothing stale. Servers that stay up but miss a message are covered by the short L1 TTL.

Why is the outbox pattern used instead of "write the DB, then publish the event"?Show answer

Two separate steps can half-fail. If the app crashes after the DB write, the event is never sent and caches stay stale. Writing the outbox row in the same transaction makes the event as durable as the change.

Size a cache: 20 M products, 2 KB each, 20% hot, 1 replica.Show answer

20 M × 2 KB × 0.2 = 8 GB hot data; × 1.5 overhead = 12 GB; × 2 for the replica = 24 GB; ÷ 0.7 headroom ≈ 34 GB: two 32 GB nodes, or more for throughput.

A CDN shows a high hit ratio but users report the wrong language. What happened?Show answer

The language isn't in the cache key. The first visitor's language is served to everyone. Add Vary: Accept-Language or put the language in the URL (/hi/p/12).

Why keep rate-limit counters and locks out of an LRU cache?Show answer

Eviction can delete them under memory pressure, which resets limits or releases locks early. Use a separate Redis (or noeviction / volatile-* policies) for them.
