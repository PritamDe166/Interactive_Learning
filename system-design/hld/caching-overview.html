Why Caching Exists

  • A cache keeps a temporary copy of data or a computed result in a faster, closer place so it can be reused.
  • A hit is served from the copy; a miss goes to the source and fills the cache. Hit ratio = hits ÷ requests.
  • It cuts latency, database load and cost (paid APIs, LLM calls), and raises throughput.
  • Caches live at every layer: browser, CDN, proxy, distributed cache, in-process.
  • You can't cache everything: memory is limited, the cache isn't the source of truth, and copies go stale.

    4Revise in two minutes

    Cheat-sheet

    • Same data read again and again→Cache it
    • Expensive to compute or pay for (LLM, geocoding API)→Cache the result
    • One key gets most traffic (hot key)→Serve it from cache, replicate it
    • Users far from the servers→Regional caches / CDN
    • Must always be exact (bank balance, stock count at checkout)→Read the source of truth
    • Changes every second→Little gain; don't bother (or very short TTL)
    • "How good is my cache?"→Hit ratio = hits ÷ total requests

    Corrected

    An in-process cache lives in the process's RAM (heap), not "in the CPU cache". CPU caches (L1/L2/L3) are managed by the hardware; your code can't put entries there. It is still the fastest option because there's no network hop.

    Corrected

    The note groups forward and reverse proxies. A forward proxy sits on the client side (an office or ISP); a reverse proxy sits in front of the origin. Both can cache.

    Corrected

    "Writes go to the database, not the cache" is true for cache-aside (Day 16). Write-through and write-behind (Days 17–18) write to the cache as part of the write.

    Added

    Browser and CDN caches commonly use disk/SSD as well as memory, so "disk is rarely used for caching" applies to server-side caches. "The DB crashes at around a million requests" is illustrative: the real limit depends on the query, hardware and connection pool.

    Added

    TTL (time to live) is the usual way to bound staleness, and a cache stampede (many misses at once when a hot key expires) is Day 20.

    5Test yourself

    Check yourself

    100 requests, 80 served by the cache. Hit ratio?Show answer

    80% (80 ÷ 100). Miss ratio 20%: only those 20 reach the database.

    Why doesn't adding a read replica fix latency?Show answer

    It splits the load, but every read still hits a disk-backed database. A cache in RAM answers repeated reads much faster.

    Why is the first request for a key always slow?Show answer

    The cache is empty (a cold cache): it's a miss, so it goes to the database and then fills the cache.

    Name two reasons to cache that aren't about speed.Show answer

    Cost (paid API or LLM calls, heavy computation) and protecting the backend (fewer database queries, rate limits).

    Should a bank balance be cached?Show answer

    No. It must always be fresh; a stale balance is a real bug. Read it from the source of truth.

    A celebrity's post is read worldwide. One cache in the US. Problem?Show answer

    Users far away still pay the long round trip. Use regional caches (fed by replicated data) or a CDN, so each region reads a nearby copy.
