Cache Write Strategies & Invalidation

  • Once data is cached there are two copies; every write must decide how the cache copy gets fixed.
  • Write-through: update cache and DB together before acknowledging. Fresh, but slower writes.
  • Write-behind: acknowledge after the cache, flush to the DB later. Fast, but can lose data.
  • Write-around: write only to the DB; the cache fills on the next read.
  • With cache-aside, delete the key on write; overwriting it can put an old value back.

    4Revise in two minutes

    Cheat-sheet

    • Read-after-write must be fresh→Write-through, or DB write + DEL key
    • Huge write rate, small loss OK→Write-behind (batch flush)
    • Written a lot, read rarely→Write-around
    • Using cache-aside and data changes→Update DB, then DEL the key
    • "Can the cache still go stale?"→Yes, rarely: keep a TTL as a safety net
    • Strict freshness across services→Publish change events (outbox/CDC) that invalidate

    Interviewers often ask "how do you keep cache and DB consistent?" right after "add a cache"; write-around and the invalidation race are the usual follow-ups.
    Deleting the key does not make cache-aside perfectly consistent: a slow reader can still put an old value back (see the lab). A TTL bounds how long that lasts; a delayed second delete closes most of the gap.

    Explain it out loud

    Answer before you open each card.

    Why is "update the cache on write" worse than "delete the key"?Show answer

    Out-of-order writes. Two writers can update the cache in the opposite order to the DB, leaving the older value cached. A delete can't put a wrong value in.

    Write-behind for a payments ledger: yes or no?Show answer

    No. The client is told "saved" before the DB has it; a cache crash loses money movements.

    Update DB then delete key, or delete key then update DB?Show answer

    DB first, then delete. Deleting first lets a reader reload the old row before your update lands, re-caching stale data.

    What does write-through cost you on reads?Show answer

    Nothing extra; it costs on writes (two hops) and memory (it caches data that may never be read).

    Ten services cache the same patient record. How do they all learn it changed?Show answer

    Publish an event (outbox or CDC) that each service consumes to delete its key, plus a TTL as a backstop.

    What is a "delayed double delete"?Show answer

    Delete, then delete again after a short delay (longer than a typical read). It removes a stale value a slow reader may have written in between.
