Design: Scale a Web App to Millions

  • The classic interview question: "Your app has 1 user today. Grow it to 10 million."
  • The answer is a sequence: at each size, find what breaks first and add one thing.
  • It uses everything from Weeks 1–2: DNS, load balancers, stateless servers, availability.
  • Then it previews what's next: caching (Week 3), replicas and sharding (Phase 2), queues (Phase 4).

    4Revise: how to answer a design question

    Answer in this order (about 45 minutes)

    1. Requirements (5 min). Functional: what users do. Non-functional: users, latency, availability, consistency. Write them down.
    2. Estimates (5 min). Users × requests per day ÷ 86,400 × peak factor; read/write ratio; data size per year.
    3. High-level design (10 min). Client → DNS → CDN → load balancer → stateless app → cache → database. Name each box's job.
    4. Data model and APIs (5 min). Main tables or documents, and 3–4 key endpoints.
    5. Deep dive (15 min). The part the interviewer cares about: the hot read path, the write path, a tricky feature.
    6. Bottlenecks and failures (5 min). What breaks first at 10×? Single points of failure? What happens when the cache or a region dies?

    Cheat-sheet

    • One server for everything→Fine to start; split the database out first
    • App tier full or a single point of failure→Load balancer + stateless servers (sessions in Redis or tokens)
    • Same reads over and over→Cache-aside in Redis; CDN for static and public pages
    • Primary DB busy with reads→Read replicas (accept replication lag)
    • Slow work inside a request (email, PDF, image)→Queue + background workers; return 202 Accepted
    • One data centre down = outage→Spread every tier across availability zones; autoscale
    • Users worldwide→Multiple regions + GeoDNS / latency routing
    • Writes outgrow one database→Shard / partition (Phase 2)
    The scale-ladder numbers are back-of-envelope rules, the same kind of estimate an interviewer expects you to make out loud.

    5Test yourself

    What do you add next?

    Explain it out loud

    Answer before you open each card.

    Why split the database out before adding a second app server?Show answer

    Two app servers need one shared database. Splitting first also lets each machine be sized for its job (CPU for the app, RAM and fast disk for SQL Server).

    What must change in the app before you put it behind a load balancer?Show answer

    Make it stateless. Sessions to Redis or tokens, uploaded files to blob storage, no in-memory data another server would need.

    Estimate peak requests per second for 2 million daily users.Show answer

    2 M × 50 requests ÷ 86,400 ≈ 1,160/s average; × 3 for the peak ≈ 3,500/s. With 90% reads that is ~3,150 reads/s, ~350 writes/s.

    Read replicas are added. A user edits their profile and the page still shows the old value. Why?Show answer

    Replication lag. The read went to a replica that hadn't applied the write yet. Read your own writes from the primary for a short time, or use session consistency.

    Why does a queue help with traffic spikes?Show answer

    It absorbs the burst. Requests are accepted quickly and workers process them at a steady rate, so the database isn't hit with the whole spike at once.

    What is the single point of failure left after adding two app servers behind one load balancer?Show answer

    The load balancer itself, and the single database. Use a managed or active-passive LB pair, and a database standby in another zone.
