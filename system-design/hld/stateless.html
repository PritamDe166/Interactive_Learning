Stateless Applications

  • Stateless doesn't mean "no state".
  • It means no important state lives inside one particular server.
  • Keep it in a database, a shared cache or the client's token.
  • Then every server is interchangeable: any one can handle any request.

Keep the app servers forgettable: session data, identity and files each have a better home. Press ▶ Play on a card.

Where state can live instead

Database

Durable business data: patients, orders, carts that must survive. Every server reads the same rows.

Shared cache (Redis)

Fast, shared, temporary data: sessions, carts, rate-limit counters. All servers see the same values.

Client token (JWT)

The client carries signed claims (Authorization: Bearer …). Any server can verify the signature without a lookup.

Added

The JWT trade-off: because no server stores the session, you can't easily "log someone out" before the token expires. Common fix: short-lived access tokens (minutes) plus a refresh token that is checked against a store, or a small revocation list.

Added

State didn't disappear, it moved. Redis and the database are now critical shared dependencies. They need their own replication, monitoring and capacity planning (Weeks 3 and 7).

Added

Local caches are fine. A server can keep a copy of reference data or compiled templates in memory. That's allowed as long as losing it only costs speed, not correctness.

3Revise in two minutes

Cheat-sheet

  • Stateless server→Any server can handle any request; nothing important lives only in its memory or disk
  • Login sessions→Shared store (Redis) or a signed token
  • Uploaded files→Blob / object storage, store only the key
  • Business data→The database
  • Can't change a legacy app yet→Sticky sessions, knowing users lose sessions when a server dies
  • Instant logout needed→Server-side sessions, not long-lived JWTs
  • Why it matters→Autoscaling, rolling deploys and failover all assume servers are disposable

Answer out loud before you open each card.

"Our API is stateless, so it doesn't use a database." What's wrong?Show answer

Stateless refers to the app instances. A stateless API with a stateful database is the normal design.

Why do sticky sessions make autoscaling awkward?Show answer

Users are pinned, so new servers get only new users and scaling in kills sessions. Load drifts uneven.

A server is replaced during a deploy. What happens to carts in the stateless design?Show answer

Nothing. They live in Redis; the new server reads them on the next request.

Name one new risk the stateless design introduces.Show answer

Redis becomes a shared dependency: if it's down or slow, every server is affected. It needs replication and monitoring.

How does a server validate a JWT without asking anyone?Show answer

It verifies the signature with the issuer's key and checks expiry and claims. No session lookup is needed.

When are sticky sessions still reasonable?Show answer

Legacy apps that keep session state in memory and can't be changed yet, or for cache locality. Treat them as a stopgap.
