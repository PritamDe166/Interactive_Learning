Vertical vs Horizontal Scaling

  • Scale up (vertical): make one machine bigger.
  • Scale out (horizontal): add more machines behind a load balancer.
  • Neither helps unless you scale the bottleneck: the component that saturates first.

Added

Bigger isn't linear. Doubling cores rarely doubles throughput: locks, memory bandwidth and garbage collection eat into it. The simulator models this with a 0.9 exponent.

Added

Autoscaling adds or removes instances on a metric (CPU, request count, queue depth). It only works if any instance can serve any request, which is tomorrow's topic: stateless applications.

Added

Fixing a database bottleneck means different tools: caching (Week 3), read replicas (Week 7) and sharding (Week 8). Adding app servers just sends more traffic to the same database.

Check yourself

Answer out loud before you open each card.

The API tier handles 20k RPS, the database 5k. You add 10 more API servers. What changes?Show answer

Nothing useful. The database still caps the system at 5k RPS. Scale the bottleneck.

Does horizontal scaling make the system highly available?Show answer

Only that tier. A single database, load balancer or DNS provider can still take everything down.

When is vertical scaling the right call?Show answer

When a bigger box fixes the bottleneck cheaply and the workload is hard to distribute, such as a primary database or an early-stage app.

Horizontal scaling creates which new problem?Show answer

Where does state live? A user's next request may land on a different server. That leads to stateless design.

Which metrics tell you what the bottleneck is?Show answer

Utilisation and saturation per resource: CPU, memory, connection pools, DB load, disk I/O, queue depth and rising p99.

What usually happens during a vertical resize?Show answer

A restart, so a short outage unless something else takes the traffic meanwhile.
