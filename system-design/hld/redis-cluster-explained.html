Redis from Zero: Keys, Nodes, Slots and Replicas

  • Redis is a program that keeps a big dictionary in memory and lets all your app servers read and write it over the network.
  • A key is the name you store a value under (patient:42). A node is one running Redis server.
  • One node runs out of memory and is a single point of failure. Redis Cluster fixes both: split the keys across nodes, and keep a copy of each node.
  • Every key belongs to one of 16,384 hash slots; each node owns a range of slots. Adding a node moves slots, not every key.
  • Every primary node has a replica. If the primary crashes, the replica takes over its slots in seconds.

4Revise in two minutes

Cheat-sheet

  • "Where does key X live?"→slot = CRC16(X) mod 16384; the node owning that slot range has it
  • Data outgrows one node's memory→add primaries; move some slots to them (resharding)
  • A node must not take the cache down with it→a replica per primary, on another machine
  • App asked the wrong node→MOVED slot host:port; the client updates its map and retries
  • Need several keys in one command→put them in one slot with a hash tag: {patient:42}:visits
  • Writes must never be lost→not Redis Cluster alone: replication is asynchronous
  • Smallest sensible cluster→3 primaries + 3 replicas = 6 nodes

Why 16,384 slots? Nodes regularly send each other a bitmap of the slots they own. 16,384 bits is 2 KB per message; 65,536 would be 8 KB. Clusters are designed for up to about 1,000 primaries, so 16,384 slots is plenty.

Timing in production: the default cluster-node-timeout is 15,000 ms, so expect a failover in roughly 15–20 seconds rather than the 5.7 s measured here with a 3 s timeout. Until then, keys in the dead node's slots can't be read or written.

Redis Cluster vs Sentinel: Sentinel gives automatic failover for one primary and its replicas (no sharding). Redis Cluster does sharding and failover, so you don't run Sentinel with it.

5Test yourself

Which idea is this?

Explain it out loud

Answer before you open each card.

What is a node, and why isn't one enough?Show answer

A node is one running Redis server. One node can only hold as many keys as its machine's memory, and if it dies every cached key is gone at once.

Why not just use hash(key) % N to pick a node?Show answer

Changing N changes the answer for most keys, so adding one node turns most of the cache into misses. Slots fix the key → slot mapping forever and only move whole slots between nodes.

How does an app server know which node to ask?Show answer

The client library downloads the slot map (which node owns which slot range), computes the key's slot itself and goes straight there. If the map is out of date, the node replies MOVED and the client updates its map.

A primary crashes. What happens, in order?Show answer

Other nodes stop getting replies to their pings → after the node timeout a majority of primaries mark it failing → its replica asks for votes, wins, and becomes primary for those slots → clients learn the new map. Until then, those slots are unavailable.

Can Redis Cluster lose a write it already said OK to?Show answer

Yes. The primary replies OK before copying to its replica. If it crashes in between, the promoted replica never had that write. Fine for a cache (the database is the source of truth), not for money.

What is a hash tag for?Show answer

To put related keys in one slot so multi-key commands work: in {patient:42}:profile and {patient:42}:visits only patient:42 is hashed, so both land in slot 13565.
