Redis from Zero: Keys, Nodes, Slots and Replicas

  • Redis is a program that keeps a big dictionary in memory and lets all your app servers read and write it over the network.
  • A key is the name you store a value under (patient:42). A node is one running Redis server.
  • One node runs out of memory and is a single point of failure. Redis Cluster fixes both: split the keys across nodes, and keep a copy of each node.
  • Every key belongs to one of 16,384 hash slots; each node owns a range of slots. Adding a node moves slots, not every key.
  • Every primary node has a replica. If the primary crashes, the replica takes over its slots in seconds.

4Revise in two minutes

Cheat-sheet

  • "Where does key X live?"→slot = CRC16(X) mod 16384; the node owning that slot range has it
  • "How is the slot computed?"→CRC16 (XMODEM) of the key, or of its {tag}; keep the low 14 bits (& 0x3FFF), giving 0–16383 (step by step)
  • Data outgrows one node's memory→add primaries; move some slots to them (resharding)
  • A node must not take the cache down with it→a replica per primary, on another machine
  • App asked the wrong node→MOVED slot host:port; the client updates its map and retries
  • Node replies ASK slot host:port→slot is being moved: send ASKING + the command there once; keep your map
  • Need several keys in one command→put them in one slot with a hash tag: {patient:42}:visits
  • Writes must never be lost→not Redis Cluster alone: replication is asynchronous
  • Want fewer lost writes→Use WAIT after the write, or min-replicas-to-write. These make lost writes less likely, but not impossible
  • One key is huge or hot→The cluster can't split one key. Split it yourself into several keys (one per region, or key:0 … key:N) and merge the results in the app
  • Pub/sub in a cluster→SPUBLISH / SSUBSCRIBE (Redis 7); plain PUBLISH goes to every node
  • SELECT 1 fails→a cluster has only database 0: use key prefixes instead
  • Smallest sensible cluster→3 primaries + 3 replicas = 6 nodes (with 2 primaries, one left alive isn't a majority)

Why 16,384 slots? Nodes regularly send each other a bitmap of the slots they own. 16,384 bits is 2 KB per message; 65,536 would be 8 KB. Clusters are designed for up to about 1,000 primaries, so 16,384 slots is plenty.

Timing in production: the default cluster-node-timeout is 15,000 ms, so expect a failover in roughly 15–20 seconds rather than the 5.7 s measured here with a 3 s timeout. Until then, keys in the dead node's slots can't be read or written.

Reading from replicas: a replica answers reads for its slots only after the connection sends READONLY; otherwise it replies MOVED to its primary. Clients do this for you when you ask for replica reads (in StackExchange.Redis, CommandFlags.PreferReplica). Expect slightly stale values.

On AWS ElastiCache (Redis OSS or Valkey): cluster mode disabled is a single shard, one primary with up to five replicas, reached through a primary endpoint for writes and a reader endpoint for reads. Cluster mode enabled is what this page describes: many shards, reached through one configuration endpoint, with keys in database 0 only.

Redis Cluster vs Sentinel: Sentinel gives automatic failover for one primary and its replicas (no sharding). Redis Cluster does sharding and failover, so you don't run Sentinel with it.

5Test yourself

Which idea is this?

Explain it out loud

Answer before you open each card.

Why not just use hash(key) % N to pick a node?Show answer

Changing N changes the answer for most keys, so adding one node turns most of the cache into misses. Slots fix the key → slot mapping forever and only move whole slots between nodes.

How does an app server know which node to ask?Show answer

The client library downloads the slot map (which node owns which slot range), computes the key's slot itself and goes straight there. If the map is out of date, the node replies MOVED and the client updates its map.

A primary crashes. What happens, in order?Show answer

1) Other nodes stop getting replies to their pings. 2) After the node timeout, a majority of primaries mark it as failing. 3) Its replica asks for votes, wins, and becomes primary for those slots. 4) Clients learn the new slot map. Until then, those slots are unavailable.

Can Redis Cluster lose a write it already said OK to?Show answer

Yes, two ways. The primary replies OK before copying to its replica, so a crash in between loses the write. And in a network split, a primary on the minority side keeps saying OK until cluster-node-timeout, while the majority promotes its replica. WAIT and min-replicas-to-write make this rarer, not impossible. Fine for a cache, not for money.

MOVED or ASK: what's the difference?Show answer

MOVED means the slot now belongs to another node for good: retry there and update the slot map. ASK only happens while a slot is being moved: this one key has already left, so send ASKING and the command to the new node once, and keep the map as it is until the move finishes.

One leaderboard key is overloading one node. Will adding nodes help?Show answer

No. A key lives in one slot on one node; the cluster never splits it. Split it yourself, for example one board per region (leaderboard:apac, :emea, :amer), and merge the top results in the app, since a server-side union across slots fails with CROSSSLOT.
