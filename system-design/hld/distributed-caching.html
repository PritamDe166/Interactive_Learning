Distributed Caching

  • An in-process cache lives inside each server: fastest, but every server has its own copy.
  • A distributed cache (Redis) is shared by all servers: one copy, one network hop away.
  • L1 + L2 combines both: a tiny local cache in front of Redis.
  • Redis grows with sharding (16,384 hash slots), survives failures with replicas, and restarts warm with persistence.

4Revise in two minutes

Cheat-sheet

  • Tiny, near-static lookup data→In-process L1
  • Sessions, shared state across servers→Redis (distributed)
  • Very hot keys, latency-sensitive→L1 (short TTL) + Redis L2
  • Data bigger than one node→Redis Cluster (hash slots)
  • A node can't be lost→Replicas + Sentinel / Cluster failover
  • Restart must not be cold→RDB snapshots and/or AOF
  • Simple string cache, multithreaded→Memcached is enough

5Test yourself

Which pattern fits?

Explain it out loud

Answer before you open each card.

You moved from 1 to 4 servers and users now see different prices on refresh. Why?Show answer

Each server has its own in-process cache, updated at different times. Use a shared cache, or keep L1 TTLs very short.

Why does hash % N hurt when you add a node?Show answer

Changing N changes almost every key's node, so most of the cache misses at once. Consistent hashing and hash slots move only about 1/(N+1) of the keys.

MGET user:1 user:2 fails on Redis Cluster with CROSSSLOT. Fix?Show answer

Put the keys in one slot with a hash tag: {user}:1, {user}:2 hash only the part in braces.

Can a failover lose data in Redis?Show answer

Yes. Replication is asynchronous; writes the primary acknowledged but hadn't copied yet are lost when a replica is promoted.

RDB or AOF?Show answer

RDB is compact and fast to load but can lose minutes; AOF with fsync every second loses about a second. Many setups use both.

When is an in-process cache the right answer?Show answer

Small, read-mostly data where brief differences between servers don't matter (config, country lists), or as a short L1 in front of Redis.

Sources: Week 3 notes; Redis documentation (cluster specification, replication, persistence); Microsoft Learn, HybridCache and distributed caching in ASP.NET Core. Latencies are rough orders of magnitude. The lab uses FNV-1a hashing (with a bit mixer) for illustration; Redis itself uses CRC16 for slots.
