Cache Eviction Policies

  • Memory is finite: when the cache is full, an eviction policy picks which key leaves.
  • LRU evicts the least recently used key; LFU the least frequently used; FIFO the oldest inserted.
  • TTL expiry is different: it removes keys for being old, not because memory is full.
  • An LRU cache is a hash map + doubly linked list, so every get and put is O(1).

Cheat-sheet

  • General purpose, recency matters→LRU (Redis allkeys-lru)
  • Stable hot set + one-off scans→LFU (Redis allkeys-lfu)
  • Only some keys may be evicted→volatile-* policies (keys with a TTL)
  • Cache must never drop data→noeviction: writes fail when full
  • "Implement an LRU cache"→Dictionary + doubly linked list, O(1) get/put
  • Stale-but-once-popular keys squat in LFU→Counter decay / ageing

Explain it out loud

Answer before you open each card.

Why not keep the LRU order in an array or List<T>?Show answer

Moving an item is O(n). A doubly linked list unlinks and relinks a node in O(1), and the dictionary finds that node in O(1).

Why does the list need to be doubly linked?Show answer

To unlink a node in O(1) you need its previous node; a singly linked list would have to walk from the head.

A nightly report reads every record once. Which policy protects your hot keys?Show answer

LFU. Under LRU each scanned key becomes "most recent" and pushes the hot keys out.

Expiry vs eviction: what's the difference?Show answer

Expiry removes a key because its TTL ran out; eviction removes one because memory is full. A key can be evicted long before it expires.

Redis is full and set to noeviction. What happens on SET?Show answer

The write fails with an OOM error; reads still work. Choose this only when losing keys is worse than failing writes.

What breaks LFU, and how is it fixed?Show answer

Old popularity. A key read a million times yesterday never leaves. Counters must decay over time (Redis does this).
