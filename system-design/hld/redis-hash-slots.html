How a Key Becomes a Hash Slot: CRC16 in Redis Cluster

  • Redis Cluster puts every key in one of 16,384 hash slots with CRC16(key) mod 16384.
  • CRC16 reads the key's bytes and combines them into one 16-bit number (0 to 65,535).
  • mod 16384 (divide by 16384 and keep the remainder) keeps the lowest 14 bits: that number is the slot.
  • Every client in every language gets the same slot, which is why Redis uses a fixed formula and not .NET's GetHashCode().

4Revise in two minutes

Cheat-sheet

  • "How is the slot computed?"→CRC16 (XMODEM) of the key's bytes, then keep the low 14 bits: crc16(key) & 0x3FFF
  • Key contains {…} with text inside→only that text is hashed, so related keys share a slot
  • Key contains empty {}→ignored: the whole key is hashed
  • "Why not GetHashCode()?"→randomised per process in .NET; every client must compute the same slot
  • "Only 16,384 slots: how do a million keys fit?"→a slot is a bucket: 1,000,000 keys ≈ 61 per slot; capacity comes from each node's memory
  • Every key tagged the same ({patients}:1 …)→one slot, one node: tag per entity, never one tag for everything
  • "Why 16,384?"→It is 2¹⁴. Nodes regularly send each other a bitmap (one bit per slot) of the slots they own, and at this size it is only 2 KB. That is plenty for ~1,000 primaries

The exact CRC16: Redis uses the XMODEM variant (polynomial 0x1021, start value 0, no final XOR). Clients in every language ship the same function, which is how they all compute the same slot without asking the server.

CRC16 is not a security hash. It is fast and spreads keys evenly, but it is easy to find keys that land in a chosen slot. That doesn't matter for placing cache keys.

Walk through how patient:42 becomes slot 13565.Show answer

Take the key's 10 bytes, run CRC16 (XMODEM) over them to get 29949, then keep the lowest 14 bits (mod 16384): 29949 − 16384 = 13565. The node that owns slot 13565 holds the key.

Why can't Redis clients use .NET's GetHashCode()?Show answer

.NET randomises string hash codes per process, so the same key gives different numbers on different servers and after every restart. Every client must compute the same slot, so Redis defines a fixed function: CRC16.

What do {order:9}:lines and a{}b hash?Show answer

The first hashes only order:9, so it shares a slot with every other {order:9} key. The second has empty braces, which are ignored, so the whole key a{}b is hashed (slot 13694).

There are only 16,384 slots. How can you store 1,000,000 patients?Show answer

A slot is a bucket, not one record. One million keys is about 61 keys per slot (41 to 80 in a real count), each still a separate key. What limits storage is each node's memory; add primaries and move slots to them.

Someone names keys {patients}:1 … {patients}:1000000. What goes wrong?Show answer

Every key hashes only patients, so all of them land in slot 9854 on one node. That node fills up and takes all the traffic. Tag per entity ({patient:42}:…), not one tag for everything.

Why do 1,000,000 patient keys split almost exactly into thirds on 3 nodes?Show answer

CRC16 scatters the keys over all 16,384 slots fairly evenly, and each node owns about a third of the slots. A real count gave 333,253 / 333,420 / 333,327.
