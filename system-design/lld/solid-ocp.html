Open-Closed Principle

  • Code should be open for extension but closed for modification: add new behaviour by adding new code, not by editing classes that already work and are tested.
  • The usual smell is a switch or if-chain over types that grows with every new case.
  • Common tools in C#: strategy (one class per variant behind an interface), decorator (wrap a class to add behaviour), extension methods, inheritance.
  • No design is closed against every change. Close it against the changes you actually expect.

Cheat-sheet

    
    
      
  • A switch / if-chain on a type, plan, format or channel keeps growing→strategy: one class per case behind an interface
    • 
      
  • Need logging, caching, retry or metrics around an existing service→decorator registered in DI; the service is untouched
    • 
      
  • Want a helper on a type you can't edit (string, DateTime, a library class)→extension method (no runtime switching)
    • 
      
  • Choosing an implementation at runtime by key→register all strategies; pick by key (dictionary or keyed services)
    • 
      
  • "What if we need X someday?" with no evidence→don't add the abstraction yet; refactor when the second case arrives
    • 
      
  • Interview: "how does OCP relate to plugins?"→the core knows only the interface; plugins (new classes) depend on the core, not the other way round
    •

Added
Origin: Bertrand Meyer stated the principle in 1988 (Object-Oriented Software Construction), meaning extension by inheritance. Robert C. Martin's later version relies on interfaces and polymorphism, which is how it's taught today. Martin calls plugin systems such as IDE extensions the principle in its purest form: the core doesn't know its plugins.

      
Added
Real examples people use: discounts by customer type, notification channels, payment methods, report formats, tax rules. Each is a family of variants that grows over time, which is exactly where OCP pays off.

      
Added
Strategic closure: you can't predict every change. Close the design along the axes that are already varying (here: plans and cross-cutting concerns), and leave the rest simple until a real second case appears.

    

  


  

    
Check yourself

    
Answer out loud before you open each card.

    

      
Why is editing a tested, shipped class riskier than adding a new one?Show answer
        
Every existing caller depends on it. An edit can break behaviour that already worked and forces you to re-test all of it; a new class can only affect the new case.

      
Name two ways to add behaviour to a class without editing it, and which one can be switched at runtime.Show answer
        
Decorator (switchable at runtime via DI) and extension methods (compile-time only). Strategy and inheritance also work.

      
Your PaymentProcessor has if (method == "card") … else if (method == "upi"). How do you make it OCP-friendly?Show answer
        
Define IPaymentMethod with Pay(); implement CardPayment, UpiPayment; register them and pick one by key. Adding wallets is a new class.

      
What can't a decorator do?Show answer
        
Change private or non-interface behaviour: it only sees the public interface members it wraps.

      
Does OCP mean you must never edit an existing class?Show answer
        
No. Bug fixes and refactoring are edits. OCP is about structuring code so that expected new variants don't require edits.

      
How is OCP connected to Liskov substitution?Show answer
        
Extension through interfaces only works if every new implementation honours the contract. A new strategy that throws or behaves differently breaks callers, which is an LSP failure.
