Liskov Substitution Principle

  • Anywhere the code expects a base type, you must be able to pass any subtype and still get correct behaviour.
  • "Is-a" in plain English isn't enough. A Square is a rectangle in maths, yet a Square subclass breaks code written for Rectangle.
  • Red flags: an override that throws NotImplementedException / NotSupportedException, does nothing, or quietly changes what the method promises.
  • Rule of thumb: a subtype may accept more and promise more, never demand more or deliver less.

The contract rules

    
What "behaves correctly" means, from Liskov and Wing's behavioural subtyping

    

      
Preconditions
can't be strengthened
A subtype can't demand more of its inputs. If Send accepts any message, an SMS version can't reject long ones.

      
Postconditions
can't be weakened
A subtype must deliver at least what the base promises. If Save guarantees the row is stored, a subtype can't skip it.

      
Invariants
must be preserved
Whatever is always true of the base (balance ≥ 0, width independent of height) stays true.

      
Exceptions
no new kinds
A subtype shouldn't throw exception types callers of the base can't expect, such as NotImplementedException.

Cheat-sheet

    
    
      
  • An override throws NotImplementedException / NotSupportedException→the subtype can't keep the base's promise: fix the hierarchy or split the interface
    • 
      
  • Callers check if (x is Square) before calling→substitution already failed; the type check is the symptom
    • 
      
  • A subclass adds validation the base didn't have→strengthened precondition: callers of the base will be surprised
    • 
      
  • "X is a Y" in the real world→ask "does X behave like Y for every caller?" instead
    • 
      
  • Two types share some behaviour but not all→a smaller common base or interface, plus separate types for the rest
    • 
      
  • Want to prove it→write contract tests against the base type and run them for every subtype
    •

Added
Origin: Barbara Liskov introduced the idea in a 1987 keynote on data abstraction; Liskov and Jeannette Wing formalised it in 1994 as "behavioural subtyping", with the pre/postcondition, invariant and history rules above.

      
Added
Real .NET example: arrays and ReadOnlyCollection<T> implement ICollection<T> but throw NotSupportedException from Add. Code that takes ICollection<T> and adds will crash at run time. It's both an LSP and an interface-segregation problem, which is why the read-only interfaces were introduced.

      
Added
From your notes: a "not implemented" override breaks LSP because the child can't stand in for the parent; the fix in the Parent/Child example is a shared Human base with Adult and Child subclasses.

    

  


  

    
Check yourself

    
Answer out loud before you open each card.

    

      
State LSP in one sentence.Show answer
        
Objects of a subtype must be usable wherever the base type is expected without changing the correctness of the program.

      
Why does throw new NotImplementedException() in an override break LSP?Show answer
        
Callers of the base type are promised the method works. The subtype can't keep that promise, so it can't stand in for the base.

      
Why is Square : Rectangle a violation even though a square is a rectangle?Show answer
        
Rectangle code assumes width and height change independently. Square breaks that invariant: set width 5, height 4, and the area is 16, not 20.

      
A subclass of PaymentGateway adds "amount must be under ₹10,000". Problem?Show answer
        
Yes: a strengthened precondition. Code that worked with the base (any amount) fails with the subtype. Put the limit in the base contract, or handle large amounts differently.

      
May a subtype return a more specific type or accept more inputs?Show answer
        
Yes. Promising more (covariant returns, stronger guarantees) and accepting more (weaker preconditions) is safe. Demanding more or delivering less is not.

      
How can you catch LSP violations automatically?Show answer
        
Write contract tests against the base type or interface (an abstract test class) and run the same suite for every implementation.
