Singleton

  • A class that has exactly one instance and a single global way to reach it: a private constructor plus a static Instance.
  • Fits things that really are one-per-app: configuration, a cache, a connection pool, a logger.
  • The hard part is thread safety: two requests arriving together can create two instances.
  • In ASP.NET Core you rarely hand-write one: services.AddSingleton<…>() gives one instance without the global, untestable static.

Cheat-sheet

    
    
      
  • Need one shared object in ASP.NET Core→services.AddSingleton<IX, X>() and inject IX
    • 
      
  • Must hand-write one (library, console tool)→private static readonly Lazy<T> + private constructor
    • 
      
  • Interviewer asks for thread-safe from scratch→double-checked locking with a volatile field, then mention Lazy<T>
    • 
      
  • Singleton has mutable state→make that state thread-safe (ConcurrentDictionary, locks, immutability)
    • 
      
  • Singleton needs a DbContext→never inject it; inject IServiceScopeFactory and create a scope per use
    • 
      
  • Tests interfere with each other→shared static state: switch to an injected interface
    • 
      
  • "Singleton is an anti-pattern?"→the global access is the problem (hidden dependency, hard to test); one instance managed by DI is fine
    •

Captive dependency: a singleton that receives a scoped service keeps the first request's instance forever. ASP.NET Core checks this in Development (scope validation) and throws "Cannot consume scoped service … from singleton".

      
Why volatile in double-checked locking: without it another thread could, in theory, see the reference before the object is fully built. .NET's memory model makes the plain version work on today's runtimes, but volatile (or Lazy<T>) says what you mean.

    

  


  

    
5Test yourself

    
Which one fits?

    

    
Explain it out loud

    
Answer before you open each card.

    

      
What two things make a class a singleton?Show answer
        
A private constructor so nobody else can call new, and a static access point that creates the one instance once and returns it every time.

      
Walk through how the naive version creates two objects.Show answer
        
Thread 1 checks instance == null: true. Before it assigns, thread 2 checks: still true. Both call new; the second assignment overwrites the first, and some callers hold a different object.

      
Why check for null twice in double-checked locking?Show answer
        
The outer check skips the lock once the instance exists (fast path). The inner check, inside the lock, catches the thread that was waiting while another one created it.

      
Why do many people call Singleton an anti-pattern?Show answer
        
The static Instance is a hidden global dependency: callers can't be given a fake in tests, state leaks between tests, and coupling is invisible in constructors. DI singletons keep "one instance" without those problems.

      
A singleton service injects AppDbContext. What goes wrong?Show answer
        
It's a captive dependency: the DbContext from the first request lives forever, is shared across threads (not thread-safe) and keeps tracking entities. Inject IServiceScopeFactory and create a scope when needed.

      
Is a DI singleton automatically thread-safe?Show answer
        
No. DI only guarantees one instance is created. Any mutable state inside it is shared by every request at once, so it must be protected.
