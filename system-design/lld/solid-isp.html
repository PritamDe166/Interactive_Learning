Interface Segregation Principle

  • No client should be forced to depend on methods it doesn't use.
  • A fat interface hurts both sides: implementers write stub methods that throw, and clients get coupled to methods they never call.
  • Split it into small role interfaces shaped around what each client needs, e.g. read, write, import.
  • When something needs all of them, a combined interface can inherit the small ones. Don't go as far as one method per interface.

Cheat-sheet

    
    
      
  • Implementers throw NotSupportedException / NotImplementedException for some members→the interface is too fat; split it
    • 
      
  • Test fakes need many empty methods→the class under test depends on more than it uses
    • 
      
  • A method only loops over a collection→take IEnumerable<T>, not List<T>
    • 
      
  • Some clients read, others write→separate read and write interfaces (the same idea as CQRS)
    • 
      
  • One class legitimately does everything→implement several role interfaces, or a combined one that inherits them
    • 
      
  • Ending up with one method per interface→too far: group by how clients use them

Added
Origin: Robert C. Martin formulated ISP while consulting for Xerox, whose printer software had one large job class that every task depended on. Small changes forced long rebuilds across the system; splitting the class's interface by client fixed it.

      
Added
.NET learned this too: IReadOnlyList<T> and IReadOnlyCollection<T> arrived in .NET 4.5 so read-only callers no longer depend on Add/Remove, and arrays and read-only collections stopped needing throwing implementations (see the Liskov page).

      
Added
From your notes: split a bulky generic repository into read, write and delete interfaces, recombine with a main interface that inherits them when needed, and avoid the over-applied version with one method per interface.

    

  


  

    
Check yourself

    
Answer out loud before you open each card.

    

      
State ISP in one sentence.Show answer
        
Clients should not be forced to depend on methods they do not use.

      
Name two costs of a fat interface.Show answer
        
Implementers write stubs that throw (also an LSP risk), and clients are coupled to unrelated methods: changes to those ripple to them, and their test fakes grow.

      
How is ISP different from SRP?Show answer
        
SRP looks at a class from the side of who changes it. ISP looks at an interface from the side of who uses it. One class can implement several small interfaces and still have one responsibility.

      
A PrintSummary(List<Patient> patients) only loops. What should the parameter be?Show answer
        
IEnumerable<Patient>. Callers can then pass arrays, lists, query results or generators.

      
How do you keep convenience for a class that needs everything?Show answer
        
Define IRepository<T> : IReadRepository<T>, IWriteRepository<T>. Full implementations implement the combined one; narrow clients still ask for the small ones.

      
What's the danger of applying ISP too strictly?Show answer
        
A sprawl of single-method interfaces that are hard to find and wire up. Group methods by the roles clients actually play.
