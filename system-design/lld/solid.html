SOLID Principles

  • Five guidelines for object-oriented code that is easy to change, test and extend.
  • Single responsibility · Open-closed · Liskov substitution · Interface segregation · Dependency inversion.
  • They work together: small focused classes, talking through interfaces, with implementations plugged in from outside.
  • They are guidelines, not rules. Applied mechanically they produce over-engineered code; the goal is simple code that is safe to change.

Cheat-sheet

    
    
      
  • One class changes for unrelated reasons (DB, email, rules)→S: split by reason to change
    • 
      
  • Every new type means editing a switch or if-chain in tested code→O: extend with a new class (decorator, strategy, extension method)
    • 
      
  • A subclass throws NotImplementedException or changes expected behaviour→L: fix the hierarchy
    • 
      
  • Implementers write empty or throwing methods they never use→I: split the interface
    • 
      
  • new SqlRepository() inside a service; can't test without a real DB→D: depend on an interface, inject it through the constructor
    • 
      
  • More interfaces than real alternatives, one method each→you've overdone it: keep it simple
    •

Added
The cautions in your notes: you can follow every principle and still write bad code; over-applied interface segregation ends in one method per interface; most projects have one implementation per interface, so the main practical win of interfaces is mocking in tests, not swapping databases.

      
Added
Where the name comes from: the principles were collected by Robert C. Martin around 2000; Michael Feathers coined the SOLID acronym. Liskov substitution is from Barbara Liskov (1987).

    

  


  

    
Check yourself

    
Answer out loud before you open each card.

    

      
Name the five principles and give each a one-line meaning.Show answer
        
S one reason to change · O extend without modifying · L subclasses must be substitutable · I no client forced to depend on methods it doesn't use · D depend on abstractions, not concrete classes.

      
Which two principles does constructor injection in ASP.NET Core support most directly?Show answer
        
D (the service depends on an interface) and O (you can register a different or decorated implementation without editing the service). It also makes S easier to keep.

      
A subclass overrides a method with throw new NotImplementedException(). Which principles are in trouble?Show answer
        
L: the child can't stand in for the parent. Often I too: the base type or interface promises more than every implementer can do.

      
Why did your notes call SOLID "guidelines, not rules"?Show answer
        
Followed to the letter they can still produce bad, over-abstracted code. The speaker's main advice: keep it simple and apply the principles where change is actually expected.

      
What is the most common real benefit of depending on interfaces?Show answer
        
Testability: you can inject a fake or mock. Swapping the real implementation (e.g. a different database) is rarer than people expect.

      
In an interview, how would you show SOLID rather than recite it?Show answer
        
Take one small design (booking, payments, notifications), point at a concrete smell, and show the before/after: which class changes now, and what you can test in isolation.
