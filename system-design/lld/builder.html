Builder

  • Build a complex object step by step through readable method calls, then get the finished object from Build().
  • It replaces telescoping constructors: new Appointment(p, d, t, 30, true, null, "R12", 2, false). Which true is which?
  • Build() is the one place to validate the combination, so the object you get back is always valid and can be immutable.
  • You use builders daily: StringBuilder, WebApplication.CreateBuilder(), DbContextOptionsBuilder, UriBuilder.

Cheat-sheet

    
    
      
  • Constructor with many parameters, several optional→builder (or named arguments if they're few and independent)
    • 
      
  • Rules between fields ("video needs a link", "end after start")→check them in Build(); throw with every problem listed
    • 
      
  • Same configurations built again and again→director (or static presets) that calls the builder steps
    • 
      
  • Just a DTO with a few required fields→object initializer with required / init; no builder
    • 
      
  • Test data with sensible defaults→test data builder: new AppointmentBuilder().Video().Build()
    • 
      
  • Fluent method signature→each step returns this so calls chain
    • 
    

    

      
Added
Builders you already use: WebApplication.CreateBuilder(args) → configure services → Build(); DbContextOptionsBuilder.UseSqlServer(…); EF Core's modelBuilder.Entity<T>().HasKey(…); StringBuilder.Append(…).ToString(); UriBuilder; ConfigurationBuilder.

      
Added
GoF vs fluent builder: the original GoF Builder separates a director (the steps) from builders (how each step is done, e.g. HTML vs PDF report). Today "builder" usually means the fluent style; the director is optional.

Explain it out loud

    
Answer before you open each card.

    

      
What is the telescoping constructor problem?Show answer
        
A chain of constructors, each adding one more optional parameter. Callers pass long positional lists (true, null, 2) that are hard to read and easy to swap by mistake, and combinations explode.

      
Why validate in Build() instead of in each setter method?Show answer
        
Many rules involve several fields and the order of calls is free. Only at Build() is the whole picture known, so it's the one place that can guarantee the object is valid.

      
What does a director add?Show answer
        
Reusable recipes: it calls the builder steps for a known configuration (e.g. "follow-up visit"), so callers don't repeat the same chain.

      
When is a builder overkill in C#?Show answer
        
When an object initializer with required and init properties covers it: few fields, no cross-field rules, no presets.

      
Name three builders in ASP.NET Core / .NET.Show answer
        
WebApplicationBuilder, DbContextOptionsBuilder, StringBuilder (also UriBuilder, ConfigurationBuilder, EF ModelBuilder).
