Single Responsibility Principle

  • A class should have one reason to change.
  • A "reason to change" is usually a person or team who asks for changes: the DBA, marketing, the academic office.
  • When one class serves several of them, every request edits the same file: more bugs, more merge conflicts, harder tests.
  • The fix is to split by reason to change, not to give every method its own class. Closely related responsibilities stay together.

Cheat-sheet

    
    
      
  • Class name ends in Manager, Helper, Utils, Processor→probably several responsibilities; list who changes it
    • 
      
  • A class mixes business rules with SQL, SMTP, HTTP or file I/O→move the I/O into its own class (repository, sender, client)
    • 
      
  • Unrelated features keep causing merge conflicts in one file→that file has more than one reason to change
    • 
      
  • Tests need a database and an SMTP server to check one rule→the rule is tangled with I/O; split it out
    • 
      
  • Tempted to make one class per method→stop: keep closely related methods together
    • 
      
  • Interview: "what is SRP?"→"one reason to change, meaning one actor it answers to", plus an example

Added
Defining "reason to change": Robert C. Martin, who named the principle, later phrased it as "a module should be responsible to one, and only one, actor". Asking who requests changes is more practical than counting methods.

      
Added
The limit from your notes: a class doesn't have to do only one thing. Its responsibilities should be closely related so it doesn't bloat, and splitting too far just scatters one idea across many files.

      
Added
Testing is the payoff you'll feel first: once the rule lives in EnrolmentService, a unit test needs no database or mail server.

    

  


  

    
Check yourself

    
Answer out loud before you open each card.

    

      
State SRP in one sentence, and give the "actor" version.Show answer
        
A class should have one reason to change. Put another way: it should answer to one actor (one team or role that requests changes).

      
Why does a class with several reasons to change cause merge conflicts?Show answer
        
Unrelated features (email, database, enrolment) all live in one file, so developers working on different tickets edit the same file at the same time.

      
A ReportService loads data, formats it as PDF and emails it. How would you split it?Show answer
        
Three reasons to change: data source, layout, delivery. For example ReportDataLoader, PdfReportRenderer, ReportMailer, plus a small coordinator that calls them in order.

      
Does SRP mean every class should have one method?Show answer
        
No. A class can have many methods if they serve the same responsibility. StudentRepository can have Save, GetById and Delete.

      
Where should GetDisplayName() live, on Student or a separate formatter?Show answer
        
On Student is fine: it's a simple value derived from the student's own data and changes for the same reason. Move it out only if formatting rules grow (locales, titles) and change for different reasons.

      
Which SRP benefit shows up most in daily work?Show answer
        
Easier testing and smaller, safer changes. Each class can be tested without the others, and a change touches one file with fewer side effects.
