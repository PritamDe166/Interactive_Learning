Dependency Inversion Principle

  • High-level modules (business rules) shouldn't depend on low-level modules (SQL, SMTP, HTTP). Both should depend on an abstraction.
  • The abstraction belongs to the high-level side: the domain defines IBookingRepository, the SQL project implements it. That's the "inversion": the arrow now points from detail to policy.
  • Dependency injection (passing the implementation in through the constructor) is how you wire it up. DI is the mechanism; DIP is the direction.
  • Biggest everyday payoff: you can test business rules with a fake instead of a real database.

Cheat-sheet

    
    
      
  • new SqlSomething(), new HttpClient(), DateTime.Now inside business logic→hidden dependency on a detail: ask for an abstraction instead
    • 
      
  • Can't unit-test a rule without a database or network→invert: interface owned by the domain + a fake in tests
    • 
      
  • Where does the interface go?→next to the code that uses it (domain), named in domain terms
    • 
      
  • Who creates the concrete classes?→the composition root (Program.cs / DI container), nowhere else
    • 
      
  • "We use DI, so we follow DIP"→only if what's injected is an abstraction the high-level code owns
    • 
      
  • Stable, side-effect-free code (string, Math, your own value objects)→depend on it directly; no interface needed

Added
The two statements (Robert C. Martin, 1996): high-level modules should not depend on low-level modules, both should depend on abstractions; and abstractions should not depend on details, details should depend on abstractions.

      
Added
Ownership matters: if IBookingRepository lives in the Infrastructure project, the domain still references infrastructure and nothing was inverted. Put it in the domain, name it in domain language, and use domain types in its signatures. This is the heart of Clean Architecture and Ports & Adapters.

      
Added
From your notes: a Service that creates its Repository depends on a concrete low-level class. Introduce an interface, inject it through the constructor, and the service no longer knows which repository it uses or how it works. Most projects have one implementation per interface, so the main practical win is mocking in tests.

    

  


  

    
Check yourself

    
Answer out loud before you open each card.

    

      
State DIP's two rules.Show answer
        
1. High-level modules shouldn't depend on low-level modules; both depend on abstractions. 2. Abstractions shouldn't depend on details; details depend on abstractions.

      
What exactly is "inverted"?Show answer
        
The direction of the source-code dependency. Before, the domain referenced the SQL code. After, the SQL code references an interface the domain defines, so the arrow points from detail to policy.

      
Is dependency injection the same as DIP?Show answer
        
No. DI is passing dependencies in. You can inject a concrete SqlBookingRepository and still depend on a detail. DIP is satisfied only when the injected type is an abstraction owned by the high-level side.

      
Where should IBookingRepository live in a Domain / Infrastructure / Api solution?Show answer
        
In Domain (or Application). Infrastructure references Domain to implement it; Api references both and wires them in Program.cs.

      
Why is DateTime.Now inside a booking rule a DIP smell?Show answer
        
It's a hidden dependency on a low-level detail (the system clock), so tests can't control "now". Inject a clock abstraction, such as .NET 8's TimeProvider.

      
Should every class get an interface?Show answer
        
No. Invert dependencies on volatile details (I/O, external services, time). Depending directly on stable, pure code is fine.
